## 2. Geekworm X630 V1.5 での ESP-KVM 動作結果（確認済みと未確認の区別）

### 2-1. 実機で確認できたこと [確認]

1. **10 ピン RESET 未配線（電源投入時リセットのみ）での起動**:
   - ESP-KVM は既定の GPIO23（未配線）へリセット解除を出したあと、I2C `0x0F` で `bridge: TC358743 found`、`tc358743: CHIPID 0x0000` を検出した。
   - GPIO7（SDA）・GPIO8（SCL）の外部プルアップ検出診断も通過した（オンボード `0x18` ES8311 も応答）。
2. **X630 の HPD・DDC・EDID 応答と HDMI ロック**:
   - `tc358743: EDID profile: full mode list` 書き込み後、`SYS_STATUS=0x0e` → `SYS_STATUS=0x9f (TMDS=1 HDMI=1 SYNC=1 DDC5V=1)` に遷移し、`video: HDMI ready SYS_STATUS=0x9f after 0 ms` でロックした。
   - これにより、X630 V1.5 上で TC358743 の `HPDO` → HDMI HPD 経路および DDC/EDID 応答が機能していることを間接的に確認した。
3. **27MHz 基準クロック・2 レーン CSI・RGB888 でのキャプチャ継続**:
   - `video: input 1920x1080p30 (htotal 2200 vtotal 2250)`
   - `video: CSI rgb888 24bpp ring 2x6220800 bytes for up to 1920x1080 (align 64)`
   - `video: capture running at 1920x1080`、`video: codec: mjpeg`、`cec: on, logical address 0`
   - 起動後約 23.3 秒間（`3.5s`〜`26.8s`）の監視中、ESP-KVM の 2 秒フレームタイムアウト（HPD 再接続リカバリ）は **0 回** であり、直後のレジスタダンプでも `CSI_ERR (0x044C) = 0x00000000`、`CSI_STATUS (0x0410) = 0x1244 / 0x1044`（`TxAct` ビットが動的に変化、`Hlt=0`）であった。
   - これにより、X630 の水晶（刻印 `27.000`）が TC358743 の REFCLK（27MHz）として機能し、TC358743 の CSI 送信側（`TxAct` のトグル、`CSI_ERR=0`）が稼働していることが確認された。なお、15pin↔22pin 同梱 FPC 経由での ESP32-P4 側の MIPI CSI 実フレーム受信は、この A-0 時点では ESP-KVM 内部ログからの間接確認にとどまり、自前コードでの直接確認は後続の PR #78（A-2 / P2b-4）で初めて完了した。
4. **ESP32-P4 再起動時の X630 状態保持**:
   - USB 給電を保ったまま `esptool` で読み出し専用ファームウェアへ書き換えて ESP32-P4 をリセットしても、X630 の `ESP_3V3` 給電は切れず、TC358743 の EDID・PLL・CSI 送信・HDMI ロック（`SYS_STATUS=0x9F`）がすべて維持されることを確認した（手順書の `[推測]` を実機で実証）。
5. **元のバックアップ（`e6891e3-dirty`）書き戻し後の Ubuntu 側の見え方**:
   - 元のファームウェア（P2b-3 マージ前の `e6891e3-dirty`）に戻したあと、Ubuntu 側で `/sys/class/drm/card*-*/status` を確認すると `card1-HDMI-A-1: disconnected` となった。
   - 原因: `e6891e3` の旧 `tc358743.c` は起動時に `SYSCTL` で `HDMIRST` を掛けて ESP-KVM の設定を消去したうえで、HDMI RX PHY（`PHY_EN` 等）を未設定にし、`DDC5V_MODE=0` のまま `HPD_CTL` に `0x11`（bit 4 `HPD_CTL0` + bit 0 `HPD_OUT0`）を書いていたため（動作中の ESP-KVM は `HPD_CTL=0x01`、`DDC_CTL=0x32`、`EDID_MODE=0x02`、`PHY_EN=0x3F`）。なお、統合ブランチにマージ済みの P2b-3（`components/tc358743/tc358743_start.c`）では `HPD_CTL` の bit 0 のみ更新（`0x01`）、`DDC_CTL`（`0x02`）、`EDID_MODE`（`0x02`）、`PHY_EN`（`0x01`）へ修正済みである。

### 2-2. 未確認の項目 [未確認]

- **Web UI 上での実映像（`frame.jpg` / MJPEG ストリーム）の目視確認、実効 fps、表示遅延**: テスト中に Ethernet リンクが上がらなかったため HTTP/Web UI 経由の取得は未実施（シリアルログ上の `capture running at 1920x1080`・タイムアウト 0 回・`CSI_ERR=0` までの確認）。
- **ESP-KVM 上での `720p60` 入力モード**: ESP-KVM の既定 EDID が `1920x1080p30` を優先 DTD として広告し Ubuntu が自動選択したため、A-0 のダンプ条件は `1920x1080p30`（同じ 972Mbps・2 レーン・RGB888）。`720p60` 限定 EDID での PC 認識とロック確認は A-1（P2b-3 実機確認）で実施する。
- **`VDD_MIPI_DPHY` の実測電圧値**: 上記 1 章のとおり極小部品の短絡防止のため未測定（`TODO(hw-verify)`）。

## 4. 参照ノートとの主な差異・P2b-3 以降への示唆（重点整理）

1. **`HPD_CTL (0x8544)` の bit 4（`HPD_CTL0`）を触らないことの実証**:
   - 動作中の ESP-KVM の読み値は `0x01`（bit 0 `HPD_OUT0=1` のみ、bit 4 `HPD_CTL0=0`）であり、この設定で X630 + Ubuntu のディスプレイ認識と TMDS ロック（`SYS_STATUS=0x9F`）が成立した。
   - 一方、旧骨格ファームウェア（`e6891e3`）は `HPD_CTL=0x11` を書いており（かつ HDMI PHY 未設定・`DDC5V_MODE=0`）、書き戻し直後に Ubuntu が `disconnected` に戻った。
   - 統合済みの P2b-3（`components/tc358743/tc358743_start.c`）は `update8(ops, HPD_CTL, 0x01, ...)` として bit 4 を保持しており、実機ダンプと完全に整合している。
2. **RMW（Read-Modify-Write）で保持される電源投入時既定ビットの存在**:
   - `CONFCTL = 0x0C17`（上位 `0x0C14` 保持）、`PHY_CTL0 = 0x20`、`DDC_CTL = 0x32`、`HDMI_DET = 0xC1`、`HDCP_MODE = 0x26`、`VI_MODE = 0xE6`、`HV_RST = 0x04` など、多くのレジスタに非ゼロの初期ビットが存在する。
   - 丸ごと上書き（`write8`/`write16`）すると未公開の初期ビットを潰す恐れがあるため、`tc358743_start.c` のように対象マスクだけを `update8` / `update16` で書き換える方針が安全であることが実機値からも裏付けられた。
3. **自己クリア・ステータス併用の制御レジスタ（読み戻し検証時の注意）**:
   - `STARTCNTRL (0x0204)` は `1` を書いたあと `0x00000000` に自己クリアされる。
   - `CSI_START (0x0518)` は `1` を書いたあと `0x00000004` として読める。
   - `PLLCTL1 (0x0022)` は RMW 対象ビット設定値 `0x0013` に対し動作中の読み値が `0x0213`、`PHY_EN (0x8534)` は対象ビット設定値 `0x01`（bit 0）に対し動作中の読み値が `0x3F` として読める（A-0 で確認したのは動作中の読み値であり、`0x01` の直接上書きは未確認）。
   - したがって、A-1 以降の実機診断でこれらをリードバックする際、「書いた値そのまま（`1` や `0x0013`）が返らない＝書き込み失敗」と誤判定しないよう注意する。
4. **`CSI_CONFW (0x0500)` 間接書き込みの実効結果の確認**:
   - 間接書き込み先である `CSI_CONTROL = 0x0000BE82`、`CSI_ERR_INTENA = 0x000003BF`、`CSI_ERR_HALT = 0x000000AD`、`CSI_INT_ENA = 0x00000004` を直接読み出し、4 回の `CSI_CONFW` コマンドが X630 上の TC358743 でノート §3-3 の意図どおり反映されることを確認した。
5. **`TXOPTIONCNTRL (0x0238) = 0`（非連続クロック）の確認**:
   - 参照ノート §9-1 項 1 で Linux ドライバとの差として挙げられていた `TXOPTIONCNTRL` は、実機稼働中の ESP-KVM で `0x00000000`（非連続クロック）であり、`CSI_ERR = 0` で安定動作していた。A-1 / A-2 でもまず `continuous_clock = false`（`0`）を基準とする。
6. **`V_SIZE (0x858C/8D)` の単位**:
   - 1080p30（総ライン数 `1125`）に対して `V_SIZE` は `2250 (0x08CA)` と **2 倍（半ライン単位）** で返る（ESP-KVM のログも `vtotal 2250` とそのまま表示）。A-4（解像度変化の追従）で `V_SIZE` を参照する場合は、有効ライン数 `DE_WIDTH_V`（`0x8588/89` = `1080`、1 ライン単位）と混同しないこと。

# 引き継ぎ資料: OS-less 4ch IP-KVM (ESP32-P4)

最終更新: 2026-10-16
この文書は、設計検討フェーズ（Claude チャット）から実装フェーズ（Claude Code）への引き継ぎ用です。
「決定事項」は変更しない前提で実装し、「要検証」「未確定」は推測で埋めずに人間へ確認してください。

## 1. 目的

LinuxベースのPiKVMの代わりに、**ベアメタル(FreeRTOS)環境の ESP32-P4** で、最小構成の IP-KVM を自作する。
**4台のPCを1台の KVM で管理**し、映像・キーボード/マウス・電源制御(ATX)を Web とハードウェアパネルの両方から操作できるようにする。

- 目的は「実用品を作る」ことと「自作の経験を積む」ことの両立。**ESP-KVM を参考にしつつ、ゼロから書く。**
- 低遅延と、ターゲットPC側にソフト(エージェント)を一切入れずに BIOS まで操作できることを重視する。

## 2. ハードウェア（決定事項）

| 項目 | 内容 |
|---|---|
| ボード | Waveshare ESP32-P4-ETH（100M Ethernet, USB 2.0 OTG HS, MIPI-CSI, 32MB PSRAM, 32MB flash, microSD） |
| **チップ rev** | **v1.3**（esptool 5.6.0 の `chip-id` で確認済み）。ビルドは rev < 3.0 系を選ぶ |
| HDMI キャプチャ | TC358743 搭載 HDMI→MIPI-CSI-2 ボード（Geekworm C790 など。2レーン） |
| HDMI 切替 | AliExpress で購入した 4ch HDMI KVM（**型番不明**）を前段に置く |
| ATX 駆動 | 74HC139 ×2 + フォトリレー×8（TC74HC157AP は機能的に不適、CD74HC4052 も検討したが 74HC139 方式を採用） |
| パネル | LED 付きモーメンタリボタン×4（切替先の選択と表示） |

接続:
- ボードの USB-C のうち **UART / USB-JTAG 側**: 書き込み・ログ用（開発機に接続）。
- ボードの USB-C のうち **OTG 側**: KVM 経由でターゲットPCに接続（HID デバイスとして認識させる）。
- 開発環境: macOS。書き込み例: `esptool --chip esp32p4 -b 921600 write-flash ...`（ポートは `/dev/cu.usbmodem*`）。

## 3. 設計の決定事項

### 3.1 切替先の決め方

**「KVM の LED を状態の真実とし、ATX の選択先はそれに追従する」で確定。**

- 切替操作（Web・パネルのどちらからも）は、ESP が KVM のボタン端子をフォトリレーで押して行う。
- KVM 本体のボタンが手で押された場合も、LED の変化を読み取って ATX 側を追従させる。
- パネルの LED と Web の表示は、ESP が読み取った LED の結果に合わせる（KVM の LED の生信号をそのまま表示しない）。

### 3.2 信号と GPIO（番号は未確定）

A0/A1 は 3 つのデコーダ区画で共有する。

| 信号 | 方向 | 本数 | 備考 |
|---|---|---|---|
| A0, A1 | 出力 | 2 | 100kΩ プルダウンで起動中の状態を確定 |
| ĒPWR, ĒRST, ĒKVM | 出力 | 3 | 各 10kΩ で 3.3V へプルアップ（起動中は必ず非選択） |
| KVM LED 1〜4 | 入力 | 4 | フォトカプラ経由で絶縁 |
| パネルボタン 1〜4 | 入力 | 4 | プルアップ + デバウンス |
| パネル LED 1〜4 | 出力 | 4 | |
| 合計 | | 17 | 足りなければ I2C IO エキスパンダ (MCP23017 等) へ |

デコーダ構成:
- 74HC139 #1: 1/2 を Power 用、2/2 を Reset 用。
- 74HC139 #2: 1/2 を KVM ボタン押下用。

注意:
- 74HC139 は 3.3V 駆動。出力はアクティブ Low、Ē が High なら全出力 High（リレーは全オフ）。
- フォトリレーの入力 LED は 3.3V から抵抗経由で、デコーダ出力でシンク駆動する。**74HC139 のシンク電流は数 mA 程度なので、入力電流の小さいフォトリレーを選ぶか、トランジスタを追加する**（部品選定時に要確認）。
- GPIO の具体的な割り当ては、ESP-KVM の `components/kvm_board/include/kvm_board.h` と Waveshare ボード回路図を見て空きを確認してから決める。

### 3.3 ファームの状態機械と不変条件

- **IDLE**: A0/A1 = LED から読んだ現在チャンネル。
- **SWITCH(n)**（Web・パネル共通）:
  1. ATX をロックする。
  2. A0/A1 を n にして、ĒKVM で 100〜200ms パルスを出す（KVM ボタン押下）。
  3. LED が n になるまで待つ（タイムアウトあり）。
  4. TC358743 の再同期を待ってから、ATX を解除する。
  5. タイムアウトしたら失敗とし、A0/A1 を実際の LED 値に戻す。
- **手動切替の追従**: KVM 本体のボタンで LED が変化したら、ATX をロックし、LED が安定してから A0/A1 を追従させる。
- **ATX(n, 操作)**: ロック中でなく、n が現在チャンネルと一致するときだけ実行する。パルスの直前・直後に LED を再確認し、不一致なら即中断する。

**不変条件（必ず守る）**
1. 切替中を除き、A0/A1 は KVM の LED から読み取った現在チャンネルと常に一致させる。
2. 切替中（ボタン押下〜LED 確定 + HDMI 再同期）は、ATX の Ē を Low にしない。
3. ATX のパルス直前と直後に LED を再確認し、不一致なら中断する。パルス長には上限を設ける。

パルス長の目安: Power 約 200〜500ms、Reset 約 200ms、強制断（約 5 秒）は別 API とし、上限をファームで固定する。

> 補足（2026-10-15）: 再同期タイムアウト時の ATX 解除、A0/A1 の変更順序（不変条件 4）、UNKNOWN 状態などの追加決定は `docs/PLAN.md` 4 章を参照。

### 3.4 API 案

| API | 内容 |
|---|---|
| `GET /api/v1/kvm/status` | 現在チャンネル、切替中かどうか |
| `POST /api/v1/kvm/select` | `{channel: 1-4}` |
| `POST /api/v1/power/press` / `reset` / `force` | **`{channel: n}` を必須**にし、現在チャンネルと違えば 409 を返す（古い画面からの誤操作を防ぐ） |
| `WS /video` | 映像フレーム（JPEG または H.264） |
| `WS /ws` | キーボード・ポインタ入力 |

### 3.5 パネル仕様

- ボタン n を押す → 切替要求。切替中は LED n を点滅。
- 成功したら LED n を点灯。タイムアウトしたら、エラー表示のあと、実際の LED が示すチャンネルの点灯に戻す。

## 4. 技術的な前提と注意点

出典はいずれも ESP-KVM（https://github.com/espkvm/espkvm）の README とドキュメント。**数値は ESP-KVM 作者の rev v1.3 実機での計測値で、自機では未検証。**

- **映像の上限**: TC358743 とのリンクは 2 レーン 972Mbit/s、RGB888 で約 81Mpix/s。つまり実質 **1080p30 が上限**。ESP-KVM は上限を超えるモードを広告しない EDID を手作りして回避している（広告しすぎるとフレームが完成せず黒画面になる）。
- **ISP の最大入力は 1920x1080**（`esp_cam_sensor` の注記）。
- **rev v1.3 では H.264 が遅い**: CSI が YUV420 を出せず、H.264 エンコーダが RGB を受け付けないため、PPA で色空間変換が必要。ESP-KVM の実測では 1080p で MJPEG 約 20fps、H.264 は 5〜7fps（1フレーム 145ms のうち 76ms が変換）。H.264 は速度ではなく低帯域のための選択肢。
  - 動きのある画面の帯域: MJPEG 約 8.5Mbit/s、H.264 約 0.5Mbit/s。
  - **MJPEG を主、H.264 を副（低帯域モード）**として実装する。
- **H.264 のブラウザ再生には WebCodecs が必要で、secure context（HTTPS）でしか使えない**。HTTPS（自己署名）は必須とする。RTSP はブラウザで再生できないので採用しない（元仕様から変更）。
- **HID**: ブートプロトコル対応キーボード + 絶対座標ポインタ + 相対ポインタ（+ 必要なら consumer keys）の複合デバイス。絶対ポインタは BIOS で効かない場合があるため、相対ポインタのフォールバックが必須。
- **KVM 経由の USB**: 安価な4ch KVM は、絶対座標マウスや USB ストレージ（仮想メディア）を通さない可能性がある。**実機で確認が必要。** 仮想メディアは当面スコープ外とする。
- **チップ rev の影響**: ESP-KVM では rev 3.0 未満と 3.0 以上が排他的なビルドターゲットになっている。自機は v1.3。
- **TC358743 の初期化**（PLL 分周、MIPI タイミングカウンタ、HPD と CSI 送信器の起動順）と、**ESP32-P4 の `MIPI_CSI_BRIDGE` レジスタの直接設定**は、公式 API だけでは足りず、最大の難所。一次情報は Linux カーネルの `drivers/media/i2c/tc358743.c` と東芝の TC358743XBG 機能仕様書。ESP-KVM / p4kvm（https://github.com/jrowny/p4kvm）の `components/tc358743` と `video_pipeline` を読んで理解することは歓迎するが、**コードはゼロから書く**こと。
- **ライセンス**: ESP-KVM と p4kvm は Apache-2.0。ソースを直接コピーする場合は LICENSE/NOTICE の表示を保持する。方針は「読んで理解し、自分で書く」。

## 5. 実装順序（リスクの高い順）と完了条件

元の依頼では「最初に TinyUSB の HID から」だったが、**最大のリスクは映像なので、順序を変更した。**

| # | フェーズ | 完了条件 |
|---|---|---|
| 1 | ESP-IDF 雛形 + `sdkconfig`（rev v1.3） | 空プロジェクトがビルドでき、書き込んでブートログが出る。ESP-IDF は ESP-KVM に合わせて 6.0.1 を第一候補とする |
| 2 | **TC358743 で CSI のフレームを1枚取得**（KVM 抜き、PC 直結） | 取得フレームを JPEG 等で保存/確認できる。PC 側の解像度変更も追従できる |
| 3 | MJPEG ストリーミング + HTTPS + WebSocket | ブラウザで映像が見える。HTTPS 必須 |
| 4 | HID（ブートキーボード + 絶対/相対ポインタ） | ターゲットPCの BIOS でキー入力・クリックが通る |
| 5 | KVM 経由に変更し、解像度変更の追従を確認 | KVM でチャンネルを手動切替しても映像が復帰する |
| 6 | ATX 4ch + KVM 切替 + パネル | 3.3 の不変条件を満たしたまま、Web とパネルの両方から切替・電源操作ができる |
| 7 | H.264（低帯域モード） | 設定で MJPEG/H.264 を切り替えられる |

各フェーズは小さいコミットで区切り、フェーズ完了ごとに動作確認の結果を記録する。

## 6. 未確定事項（人間への確認が必要）

1. **KVM のボタン端子の電圧**（3.3V / 5V）と、押下で GND へ落ちること。4ボタンが独立か（共通線のあるマトリクス配線ではないか）。
2. **KVM のチャンネル LED の駆動電圧と極性**（アクティブ High/Low、点灯時の電圧）。
3. **ESP32-P4-ETH の空き GPIO**（ESP-KVM のピンマップと Waveshare の回路図で確認）。
4. フォトリレー・フォトカプラの具体的な型番と抵抗値。
5. ESP-IDF のバージョン（6.0.1 で `esp_video` / `esp_cam_sensor` が自機 rev v1.3 で動くか）。
6. KVM 経由で絶対ポインタが通るか。

## 7. 作業ルール（Claude Code 向け）

- **ハードウェアの電気的な数値（電圧、極性、電流）を推測で確定しない。** 未確認のものは `TODO(hw-verify)` として残し、人間に確認する。
- **ATX 制御は安全側に倒す**: Ē のプルアップを前提とし、パルス長に上限を設け、`channel` 不一致は拒否する。
- **セキュリティ**: 認証なしで操作を受け付けない。初期パスワードのままでは先に進ませない。インターネットに直接公開しない前提（VPN 越し）をドキュメントに明記する。
- 状態機械（3.3）は、ハードウェアに依存しない形で書き、**ホスト（macOS）上でユニットテスト**できるようにする。
- 不明点や、この資料と実機の挙動が食い違う場合は、実装を進める前に報告する。
- 使用モデルは **Sonnet または Haiku** とする（ユーザー指定）。

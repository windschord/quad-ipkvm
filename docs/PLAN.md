## 4. 仕様の追加決定（HANDOFF 3.3 への補足）

本節が HANDOFF 3.3 の補足の唯一の置き場（HANDOFF 側にはここへの参照だけを置く）。

**合意済み（オーナー承認）**
- **切替後の HDMI 再同期待ちにはタイムアウトを設ける。タイムアウト／無信号でも ATX のロックは解除する。**
  理由: 電源オフのターゲットは無信号のままであり、ATX で起動できなくなるのを防ぐ。映像状態は「無信号」として API で通知する。
  手動切替の追従でも同じ再同期待ち（上限あり）を行う。タイムアウト値はパラメータ化し `TODO(hw-verify)`。
  （不変条件 2 の「切替中」= ボタン押下〜LED 確定 + 再同期待ち（上限あり）。）

**Opus レビューによる安全側の追加（TB-1 の必須要件。異論があれば差し戻し可）**
- **不変条件 4（A0/A1 の変更順序）**: A0/A1 は 3 つのデコーダ区画で共有のため、いずれかの Ē が Low の間は A0/A1 を変えない。
  変更は「全 Ē を High → A0/A1 変更 → セットアップ時間を置く → 必要な Ē を Low」の順。
- **UNKNOWN 状態**: LED が全消灯・複数点灯・チャタリング・起動直後など「現在チャンネルを確定できない」間は UNKNOWN とし、ATX ロック・全 Ē High・A0/A1 保持。LED 安定判定時間はパラメータ（`TODO(hw-verify)`）。
- **競合シナリオの期待動作を表で定義しテストと 1 対 1 対応**: 切替中の手動切替、タイムアウト後に LED が遅れて n になる、ATX パルス中の LED 変化、切替要求の重複（Web とパネル同時／現在チャンネルへの切替）、切替中の ATX 要求。
- **パルス中の LED 監視**: パルス中も LED を周期監視し、不一致なら即座に Ē を High に戻す。「直後の再確認」は異常として記録・通知する定義に改める（出し終えた後では中断できないため）。
- **パルス長上限の多重防御**: ロジック側と `kvm_board` 側の双方で上限を clamp し、`kvm_board` はハードウェアタイマー（esp_timer one-shot 等）で自動解放する。

## 4.1 `kvm_logic` の設計方針（TB-1）

- 言語/テスト: **C99 + Unity + CTest に固定**（Unity はバージョン固定で vendoring か FetchContent）。`-Wall -Wextra -Werror` と ASan/UBSan を有効化。テストは自動発見し、テスト追加で `ci.yml` を編集しない。
- `kvm_logic` は IDF ヘッダを include しない。IDF ビルドにも含め、ターゲット(RISC-V)でコンパイルできることを保証する。
- **ブロッキング禁止の純関数**: `kvm_logic_step(state, event, now_ms) -> actions`。時刻は単調増加 `uint64_t` ms を外部注入（`uint32` を使う箇所はラップアラウンドのテストを追加）。
- HAL は `set_addr` / `set_enable(sel, level)` / `read_led_raw` / `video_sync_state` 程度の小さな interface。`video_sync_state` は `LOCKED / NO_SIGNAL / UNKNOWN`（実装は P5）。
- 実行モデル: 1 つの kvm タスクが状態を占有し、Web/パネルはキュー経由で `channel` 付きコマンドを投げる。**`channel` の照合（409 判定）はロジック内で行う**（TOCTOU 回避）。
- HID の入力変換は別の純粋コンポーネント（`hid_logic`）に置く（P4）。`kvm_logic` に混ぜない。

## 4.2 P3 の設計方針（案 1・オーナー合意済み）

- **映像ソースの抽象化**: `video_source`（JPEG フレームを供給する）を定義し、P3 では**テストパターン**（組み込みの固定 JPEG を一定 fps で供給）を実装する。P2b 完了後に実ソースへ差し替える。
- **ネットワーク**: Ethernet（IP101GRI、RMII、DHCP）を `net_eth` として P3-0 で初期化する（HANDOFF の 100M Ethernet。タスクの抜けとして P3 計画時に追加）。
- **証明書**: **初回起動時に自己署名証明書を生成**して NVS に保存する（秘密鍵をビルドに埋め込まない）。ブラウザの警告は想定どおり（ドキュメントに明記）。NVS は平文なので、フラッシュ暗号化は本計画の範囲外とし、その旨をドキュメントに明記する。
- **初期パスワード**: **初回アクセス時にパスワード設定を強制**する。設定が済むまで、設定 API 以外は 403。設定は一度だけ受け付ける（競合しても二重に設定できない）。
- **認証**: パスワードはソルト付き PBKDF2-HMAC-SHA256（本番は mbedTLS）で保存し、ログインでセッショントークンを発行する。トークンは Cookie（`HttpOnly; Secure; SameSite=Strict`）。トークン自体は保存せず、ハッシュだけを保持する。セッションは最大数・アイドルタイムアウト・絶対期限あり。ログイン試行は回数を制限する（バックオフ・ロックアウト）。パスワードとトークンはログに出さない。
- **CSRF / オリジン**: 状態を変える POST と WebSocket のアップグレードで、`Origin` を検証する。
- **配信**: `WS /video` は JPEG のバイナリフレームを送る。クライアントごとに、送信が遅れたら古いフレームを捨てて最新だけを送る（遅延を溜めない）。同時接続数に上限を設ける。
- **最小ビューア**: ログイン/初回設定の画面と、WebSocket の JPEG を `<canvas>`/`<img>` に描画するだけの静的ページ。厳格な CSP を付け、動的な HTML 生成や `eval` は使わない。本格的な Web UI は範囲外。
- **テスト方針**: 認証ロジックと `frame_hub` は IDF 非依存の純 C にして、ホストテストとファズで検証する（TB-1 と同じ手法）。暗号プリミティブのホスト用参照実装は**テスト専用**とし、標準テストベクタで検証する。本番は mbedTLS のみを使う。

## 4.3 実機ブリングアップ後の決定事項（オーナー合意 2026-10-22）

- **PBKDF2 の所要時間（`docs/HW_VERIFY.md` D5、`docs/AUTH_DESIGN.md`）**: 計測の結果、`-O2` で約 8%、HW SHA 無効で約 25% 短縮するだけで、10000 回は約 0.63〜0.85 秒（1 反復 63〜86µs）。**決定: 反復回数は下限の 10000 回を維持。HW SHA は、TLS などへの影響が未測定のため無効にしない。`web_server` は、ハッシュ計算を `httpd` のタスク上で同時に 1 本だけ実行し、実行中の別要求には `503` と `Retry-After` を返す（専用ワーカータスクは #49 により実装済み）。** ウォッチドッグの設定を緩める案、PBKDF2 の自前実装、10000 回未満への引き下げは採らない（旧 `mbedtls_pkcs5_pbkdf2_hmac` は Mbed TLS 4 で削除済み）。
- **TC358743 の RESET と INT は配線する**: X630 の **10 ピン機能コネクタ**（SH1.0）にある（4=INT〔active high〕、5=RESET〔active low〕、10=GND。1=3V3 出力。出典はメーカーの Wiki で、`docs/HW_VERIFY.md` E4）。ESP の GPIO を 2 本割り当てる（B 章。合計 19 本）。信号レベル・プルアップ・起動時の状態は `TODO(hw-verify)`。**配線が済むまでは、P2a / P2b は配線なしで書く**（ソフトリセット＋I2C での割り込みステータスのポーリング）。配線後に `tc358743_config_t` へ `reset_gpio` / `int_gpio` を足し、INT を KVM 切替後の再同期待ち（P5）のイベントに使う。
- **YUV422 と 1080p50**（HANDOFF 4 章の「1080p30 上限」は RGB888 前提）: 2 レーンの帯域だけなら YUV422（16bpp）で 1080p50 が収まる計算（未検証）。ISP / JPEG エンコーダが受け付ける入力形式と、100Mbps の Ethernet が実際のボトルネックになりうる。**P2b の着手時に確認する**（先送り）。

## 4.4 OLED 表示と I/O エキスパンダ（オーナー合意 2026-10-25）

> OLED-3（IDF との結合）の設計と、ESP-IDF v6.0.1 で確認した事実、判断が必要な点は **`docs/OLED3_PLAN.md`**。

HANDOFF の範囲に、**状態表示用の OLED** と、パネル用の **I/O エキスパンダ（MCP23017）**を追加する。**電気的な数値（I2C アドレス、電源電圧、プルアップ、端子の電流）は、実機で確認するまで確定しない**（`TODO(hw-verify)`、`docs/HW_VERIFY.md` G 章）。

### 部品と接続

- **表示器**: SSD1306 の 128x64 単色 OLED。**I2C 接続**で、TC358743（アドレス 0x0F）と**同じ I2C バスに並列**に繋ぐ（GPIO を消費しない）。アドレスは 0x3C か 0x3D（`TODO(hw-verify)`）。
- **I/O エキスパンダ**: **MCP23017**（16 ポート、I2C）。**オーナーの決定（2026-10-25）**。調達する商品: スイッチサイエンス `products/1650`「MCP23017 Raspberry Pi 用 GPIO エクスパンダ」（SSCI-016506）。**商品ページの記載（`HW_VERIFY` G1 の出典）**: 動作電圧 1.8〜5.5V、16 ポート（8 ポート×2）で各ポートは独立に入出力を設定でき、**I2C のプルアップ抵抗用のパターンはあるが、抵抗は未実装**、アドレス設定用のはんだジャンパ×3 で**初期アドレスは 0x20**、面実装部品は実装済み、付属の 1×40 のピンヘッダ（ライトアングル）は自分ではんだ付けする。**`INTA`/`INTB`（割り込み）と `/RESET` の端子が引き出されているかは、ページからは分からない**（回路図の PDF で確認する。`HW_VERIFY` G4）。
  - 検討した案: PCF8574（8 ビット、準双方向、リセット端子なし）。**端子数（表示切替ボタンで 9 本になり 1 個では足りない）と、プッシュプル出力、リセット端子を理由に、MCP23017 を採る。**
- **アドレス**: MCP23017 は 0x20〜0x27（初期 0x20）。OLED（0x3C/0x3D）、TC358743（0x0F）と重ならない。オーディオコーデックのアドレスは未確認（`HW_VERIFY` B5）。

### GPIO の割り当て（本数。番号は P6 で確定）

| 区分 | 信号 | 本数 |
|---|---|---|
| **エキスパンダ（MCP23017）** | パネルの LED×4、パネルのボタン×4（ポート A） | 8 |
| | **表示切替ボタン**（ポート B の B0） | 1 |
| | 予備（B1〜B7。入力にしてプルアップを有効にしておく） | 7 |
| **直接 GPIO** | ATX の A0/A1、ĒPWR/ĒRST/ĒKVM | 5 |
| | KVM の LED×4 | 4 |
| | X630 の RESET/INT（B6。**GPIO16/17 のまま**） | 2 |
| | エキスパンダの INT（`INTA`/`INTB` を 1 本にまとめる。引き出されていなければポーリング） | 1 |
| | エキスパンダの `/RESET`（引き出されていれば。下記の安全機構） | 0〜1 |
| **合計（直接 GPIO）** | | **12〜13 本**（候補 23 本から JTAG の GPIO2〜5 と USB の GPIO26/27 を除いた 17 本のうち、**4〜5 本が余る**。GPIO2〜5 は使わない） |

- **X630 の RESET/INT は、エキスパンダに移さず、GPIO16/17 のまま**にする（映像の立ち上げを、エキスパンダの有無に依存させないため。GPIO には余裕がある）。**エキスパンダの予備の端子に移す案は、将来の選択肢として残す。**

### 安全上の方針（重要）

- **ATX の A0/A1・Ē、KVM の LED は、エキスパンダに置かない（直接 GPIO のまま）。** MCP23017 も、**最後に書いた出力を保持する**（`/RESET` を引くか、電源を切るまで）。ファームのクラッシュやウォッチドッグのリセットの後も、`Ē` が Low のまま残ると、ATX のリレーが入ったままになる恐れがある。直接 GPIO は、MCU のリセットで High-Z になり、**外付けの 10kΩ のプルアップでリレーが必ず切れる**（HANDOFF 3.2）。
- **KVM の LED は、「状態の真実」**（HANDOFF 3.1）のため、I2C を介さない。
- パネル（LED・ボタン）と OLED は、**表示と入力だけ**で、ATX や切替の安全には関与しない。エキスパンダや OLED が応答しなくても、Web と ATX は動く（パネルと表示だけが使えなくなる）。
- **`/RESET` が引き出されている場合**: 10kΩ で GND にプルダウンし、ESP の GPIO 1 本で、起動時に High にして解除する。**ESP がリセットされて GPIO が High-Z になると、エキスパンダも自動的にリセットされ、全端子が入力（High-Z）に戻る。** I2C が故障して、エキスパンダを操作できないときにも、ファームがこの線で強制的に解除できる。**引き出されていない場合は、この機構は使えない**（その場合も、ATX は直接 GPIO のままなので、安全性は変わらない）。
- 起動時の設定の順序: ①`IOCON` を設定、②出力のラッチ（`OLAT`）に、LED の消灯の値を書く、③その後で、方向（`IODIR`）を出力にする（出力にした瞬間の誤点灯を避ける）。

### OLED の表示仕様

- **表示は 30 秒間だけ**で、その後 OLED を消灯する（SSD1306 のディスプレイ OFF）。30 秒は設定項目（既定 30000ms）。
- **表示切替ボタン**（専用の 1 個、エキスパンダの B0）: **表示中に押すと、次のページへ**（最後のページの次は最初）。**消灯中に押すと、点灯する**。
- **消灯中の押下は、点灯のみ**で、ページは切り替えない（最初のページ＝IP を表示。誤操作の防止）。
- **押すたびに、30 秒のタイマーを戻す**（延長する）。
- **起動直後は点灯して 30 秒表示**する（初期設定で IP が必要なため）。**IP を取得したとき**は、自動で、最初のページで 30 秒点灯する。ほかのイベント（状態の変化、エラー）では自動点灯しない。
- **ページの構成**: ①IP アドレス・ホスト名・リンク（速度）、②現在の KVM チャンネル・映像ソースの状態・接続中のクライアント数、③稼働時間・ファームのバージョン・空きメモリ。
- 点灯中は、表示内容を 1Hz 程度で更新する（変化した部分だけを送る）。
- **実装の分離**: 「状態 → 表示する文字列」「文字列 → フレームバッファ（フォント含む）」「表示の状態機械（`OFF` / `ON(ページ)`、ボタン、時刻、IP 取得）」「エキスパンダのレジスタ操作とボタンのデバウンス」は、**IDF に依存しない純 C**にして、ホストでテストする。時刻の巻き戻りは、安全側（消灯）に倒す。I2C への書き込みは、薄いグルー層に置く。

### I2C バスの共有

- 同じバスに、TC358743、SSD1306、MCP23017（、オーディオコーデック）が乗る。**バスの排他制御**（IDF の I2C マスタが複数デバイスを 1 つのバスで扱うときの動作は、ソースで確認する）と、**OLED の更新で、TC358743 のレジスタアクセスを長く待たせないこと**（100kHz で、画面全体の 1KB の転送が約 0.1 秒かかる。変化した部分だけを送る）が必要。
- バスのプルアップ（ESP32-P4-ETH 側は 2.2kΩ→3.3V、`HW_VERIFY` E3）を使う。**MCP23017 のモジュールには、プルアップの抵抗が実装されていない**ため、モジュール側の追加はない。OLED のモジュール側のプルアップの有無は、`HW_VERIFY` G3 で確認する。**合成抵抗と立ち上がり時間は、実機で確認する。**
- **MCP23017 は、3.3V で使う**（ESP32-P4 は 5V 非対応。5V で使うと、出力とバスの信号が 5V になる）。
- **物理的な分岐点**: TC358743 の I2C は、X630 の 15 ピン FPC 経由で、ESP32-P4-ETH の CSI コネクタに繋がる見込み。OLED とエキスパンダの SDA/SCL を、**ピンヘッダなどから取り出せるか**は、**未確認**（G3）。

### フェーズ

- Issue #44（OLED 表示とパネルのエキスパンダ）。純 C の部分（`oled_ui`、`oled_render`、`mcp23017_logic`）は、実機なしで先に進められる。IDF との結合と実機確認は、`HW_VERIFY` G 章の確認の後。パネルのボタンと LED の**意味づけ**（切替の状態機械との結合）は、P6 で行う。

## 6. 進め方（初手）

1. docs 配置・本計画を push（完了後に Issue 起票）。
2. Jules: **T0-1 を先行**（以降のタスクが依存するため単独で）。
3. 並行して Claude が TC-1（`docs/HW_VERIFY.md`）を作成し、オーナーに実機確認を依頼（P2a のクリティカルパス）。
4. T0-1 マージ後、**TB-1 と P2a を並行**で Jules に依頼（互いに別ディレクトリ）。オーナーは P1 を実施。
5. P2b 以降は実機ログをオーナーが Issue/既存セッションに戻すループで進める。GPIO・KVM 配線の回答（Track C）を受けて P6。

## 7. Jules 運用ルール（Claude が監視）

- 依頼文は `docs/HANDOFF.md`・`CLAUDE.md`・本書・対象 Issue を必読と明記する。
- プランは評価してから承認（受入基準との整合、スコープ逸脱、既存ファイルの削除がないか）。
- PR はサマリではなく**差分全体**を読む。スコープ外の削除、テストの削除/スキップは差し戻す。
- ハードウェアの電気的数値を Jules が推測で決めた場合は差し戻し、`TODO(hw-verify)` に置換させる。
- Apache-2.0 の ESP-KVM / p4kvm のコードを直接コピーしていないか確認する（コピーする場合は LICENSE/NOTICE 保持）。
- レビュー対応は既存セッションに `send-message`（新規セッションは作らない）。
- Jules の PR は `claude/brave-cori-5m9w1m`（現作業ブランチ）を base にする。最終的にこのブランチを main へ PR する。

      2. **`40 KB/s` で両クライアントが巻き添え切断される現象**: `[52.8s]..[61.9s]` の実機ログには `esp-tls-mbedtls` / `httpd_ws` の送信エラーが**1 件も出ておらず**、代わりに `WS video requesting close on fd=52` と `fd=51`（40ms 差）が発生した。理由: 約 112 KiB の JPEG は TLS 約 7 レコード（16 KiB/record）に分割され、各ソケット書込（`TCP_SND_BUF=5760 B`）が `5760 B / 40 KB/s ≒ 144 ms < SO_SNDTIMEO(250 ms)` で**毎回部分成功**するため `httpd_ws_send_frame_async` が最後まで止まらず、1 フレーム送信に約 2.8 秒かかって単一 `httpd` タスクを専有する（`/status max = 5.1〜6.6s`）。その待ち時間で `ws_video_core` の `WS_SEND_TIMEOUT_MS=3000ms` が無実の `fd=51` に対しても発火し、両者とも閉じられた。
    - **案 3 の要否と設計提案（#82 ③、Claude へ相談）**:
      - 7 KB テストパターンでは顕在化しなかった **`40 KB/s` 帯での巻き添え遮断と `/status` 5〜6.6 秒停止** が約 112 KB の実映像で確認されたため、**案 3（映像 `/video` 用の別 `httpd` インスタンス分離、`CONFIG_LWIP_MAX_SOCKETS=16` は既に確保済み）は本命の対策として有効**。
      - さらに単一 `httpd`・案 3 のどちらを採る場合でも、(a) `sending_since_ms` をキュー投入時ではなく `httpd` コールバック開始時に更新すること、(b) `httpd_ws_send_frame_async` を 16 KiB TLS レコード分割送出しつつ**1 フレーム総送信デッドライン**（例: 250〜400 ms）を設けることで、`40 KB/s` の部分書込ループでも `httpd` タスクと他クライアントを守れる。

# ISO の仮想メディア（アップロード + USB マウント）の設計 (P8)

ブラウザから ISO をアップロードして microSD に保存し、ターゲット PC に **USB の仮想 CD-ROM** として見せる機能。**この文書が契約**（API は `docs/WEB_API.md` §8、境界は `docs/INTERFACES.md` §7）。担当: 設計・純 C・API・ビューア = Claude、SD・USB・実機 = Antigravity。

## 0. オーナーの決定（2026-11-18）と、この文書での扱い

| 項目 | 決定 |
|---|---|
| 機能 | ISO を**アップロード**し、**USB 経由でマウント**する。ISO は **microSD に保存**する |
| 対象の ISO | **Linux の ISO だけでなく、Windows の ISO も起動できる**こと → **仮想 CD-ROM のエミュレーションが必須**（ディスクとして見せるだけでは足りない。§5） |
| ISO のサイズ | **4 GiB を超える ISO も扱う**（Windows の ISO は約 5〜7 GB） |
| カード | 32GB の microSD。**FAT32 に再フォーマットして使う**（オーナーが PC で行う。デバイスは `f_mkfs` を使わない。§3） |
| 保存方式 | **FAT32 に、固定サイズのパーツに分割して保存し、連続確保（できなければ断片でも可）して、SD のセクタを直接読む**（保存方式の案 1。§12） |
| SD の用途 | 計画書の GPIO 割り当て（`PLAN.md` §4.4）に SD はない。**ISO 専用**（回路図で GPIO39〜45 を使うことを確認済み。§1） |

**変更してよいもの**: 数値（パーツの大きさ、チャンクの大きさ、各上限）は、実機の測定（`HW_VERIFY.md` I 章）で変えてよい。保存方式は、§2 の「連続した領域の一覧（エクステント）」の層が隠すので、後から別の方式（exFAT の有効化など）に切り替えても、上の層は作り直しにならない。

## 1. 確認した事実と、未確認のこと

## 3. SD の保存形式（FAT32）

オーナーが PC で FAT32 にフォーマットする（32GB のカードは FAT32 が標準。Windows 標準のツールで可）。デバイスは、フォーマットしない（誤って消すのを避ける）。**FAT32 以外（exFAT など）のカードは、`sd_unsupported_fs` として、機能を使えない状態にする**（API は 503）。

```
/iso/                       ← ルート。無ければ作る
  import/                   ← PC で ISO を直接コピーする場所（§3.3）
  <id>/                     ← 1 つのイメージ。<id> は 8 桁の小文字の 16 進（乱数）
    meta                    ← メタデータ（128 バイト固定。§3.2）
    p000, p001, ...         ← データのパーツ（連番）
```

### 3.1 パーツ
- **パーツの大きさは 1 GiB（1,073,741,824 バイト = 524,288 個の CD ブロック）**。最後のパーツだけ、残りの大きさ。FAT32 の 1 ファイルの上限（4 GiB 弱）に余裕があり、連続した空きを確保しやすい。
- イメージの最大は、パーツ 16 個 = **16 GiB**（`ISO_MAX_PARTS`）。
- **論理サイズは 2048 バイトの倍数に切り上げる**。ISO の大きさが 2048 の倍数でないとき、末尾は 0 で埋めたものとして扱う（READ CAPACITY は切り上げた値。パディングの部分は、読むと 0 を返す）。
- アップロードは、パーツを先頭から順に書く。**各パーツの最初のバイトが届いたとき**に、そのパーツを確保する（`f_expand` で連続確保を試みる。1 GiB のパーツで、FAT の更新は数万クラスタ）。**`begin` の時点で、空き容量（`size` + 予備 `ISO_FREE_RESERVE_MIB`）を検査する**（足りなければ、書き始める前に 507）。
- **連続は必須ではない**: `f_expand` が失敗しても（空きが断片化）、通常の `f_write` で書いてよい。読み出しは、`CLMT`（クラスタのリンクマップ）から作るエクステントの一覧で行うので、断片化していても動く。**エクステントの数が多すぎて `CLMT` が作れないとき**（`FR_NOT_ENOUGH_CORE`）は、そのイメージを `too_fragmented` として拒否する（削除して、空きが連続するように入れ直す）。

### 3.2 メタデータ（`meta`、128 バイト固定、リトルエンディアン）
| オフセット | 大きさ | 内容 |
|---|---|---|
| 0 | 4 | マジック `ISO1` |
| 4 | 2 | 版（1） |
| 6 | 1 | 状態: 0 = `uploading`、1 = `ready`、2 = `incomplete`、3 = `invalid` |
| 7 | 1 | 予約（0） |
| 8 | 8 | 論理サイズ（バイト。アップロードの宣言値。`ready` のとき、2048 に切り上げる前の実サイズ） |
| 16 | 8 | 受信済みのバイト数（`uploading` / `incomplete` のとき） |
| 24 | 2 | パーツの数 |
| 26 | 2 | 予約（0） |
| 28 | 4 | パーツの大きさ（ブロック数。既定 524288。将来の変更に備える） |
| 32 | 32 | SHA-256（`ready` のとき。なければ全 0 と、下のフラグ） |
| 64 | 1 | SHA-256 が有効か（0 / 1） |
| 65 | 1 | 名前の長さ（バイト。1〜63） |
| 66 | 62 | 名前（UTF-8。残りは 0） |
| 124 | 4 | 先頭の 124 バイトの CRC-32（IEEE 802.3） |

- **壊れた `meta`（マジック・版・CRC の不一致）は、そのイメージを `invalid` として扱う**（一覧に出し、削除はできるが、マウントはできない）。
- メタデータの書き込みは、**一時ファイルに書いて `rename`**（FAT32 でも、途中で電源が落ちたとき、古い方か新しい方のどちらかが残る）。

### 3.3 PC から直接コピーする（`import`）
`/iso/import/` に、PC で **4 GiB 弱までの ISO ファイル**（`*.iso`）をコピーすると、`POST /api/v1/iso/rescan`（と起動時）で、イメージとして取り込める。取り込みは **`rename` で `/iso/<id>/p000` に移す**（コピーしない。同じファイルシステム内なので速い）。名前はファイル名（拡張子を除く。名前の規則に合わないものは、`<id>` を名前にする）。`sha256` は「なし」（確認したいときは、`finish` と同じ処理を `rescan` が行う: ハッシュは SD を読み直して計算する）。**4 GiB を超える ISO は、FAT32 のファイルとして置けないので、ブラウザのアップロード（パーツに分割される）を使う**。

### 3.4 状態

```
begin ──▶ uploading ──(全バイト受信 + finish)──▶ ready
              │ アイドルのタイムアウト / 電源断 / 再起動
              ▼
         incomplete ──(再開: 同じ id に続きを PUT)──▶ uploading
 finish の検査に失敗（サイズ不一致は 409 で、状態は変わらない。SHA-256 の不一致、ISO でない）──▶ invalid（削除のみ）
```
- `hashing`（SHA-256 を計算中）は、**メタデータに保存しない実行時の状態**（API の `state` にだけ出る。再起動すると、`incomplete` に戻る）。
- **マウントできるのは `ready` だけ。**
- **マウント中のイメージは、削除も、変更もできない**（409 `mounted`）。パーツを書き込める状態にならないので、直接読み出しと FatFs のキャッシュが食い違わない。
- **`ready` になるのは、全パーツを `f_sync` と `f_close` した後**。その後で、エクステントの一覧を作る（マウントのたびに作り直す）。

## 4. SD の読み書きの排他と、性能

- **SD の I/O は、1 つのロック（`sd_io_lock`）で直列化する**。FatFs の読み書き（diskio）と、MSC の直接読み出し（`iso_blockdev_t`）の**両方**が、同じロックを取る。IDF の `esp_vfs_fat` の標準の diskio は、このロックを持たないので、**自前の diskio のラッパー**（FatFs の `ff_diskio_register` で登録するもの）で、ロックを取ってから `sdmmc_*` を呼ぶ（A-13）。
- アップロードを受信しながら、ターゲットがマウント中の別のイメージを読むことがある。ロックで直列化されるので、どちらも遅くなる（ターゲットの読み出しが遅くなっても、壊れない。**ロックの保持時間は、1 回の I/O（最大 `ISO_UPLOAD_CHUNK_KB` 分の書き込み）に限る**）。
- 1 つの CD ブロック（2048 バイト）= SD の 4 セクタ（512 バイト）。パーツの先頭はクラスタ境界（FAT32 の 16 KiB など）なので、4 セクタの境界に揃う。
- 読み出しは、`iso_extent` が「連続した SD のセクタの区間（スパン）」の一覧を返し、グルー（A-14）が区間ごとに `read_sectors` を呼ぶ。1 回の MSC の転送（TinyUSB のバッファの大きさ）の単位で、先読みはしない。**性能の目標は `TODO(hw-verify)`**（Linux の ISO のブートに足りる速度。実測する）。

## 5. USB: 仮想 CD-ROM

### 5.1 デバイスの構成
- 今の複合デバイス（HID ×3、記述子 84 バイト）に、**MSC のインターフェースを 1 つ足す**（クラス 0x08、サブクラス 0x06 = SCSI、プロトコル 0x50 = BOT。バルク IN/OUT の 2 本。HS は 512 バイト、FS は 64 バイト）。記述子は `usb_hid_logic`（純 C）で作っていて、ホストテストがある。MSC を足すと、**FS と HS の両方の設定記述子と、インターフェース数の値が変わる**ので、テストも直す。
- **LUN は 1 つ**。`USB_MSC_ENABLE`（既定 n）が有効なときだけ、記述子に入れる（無効なら、今の構成のまま）。
- **ターゲットから見えるのは、USB が接続されているとき**（`usb_vbus_ctrl` が接続させたとき）。ターゲットの電源が切れている間は、見えない（今のとおり）。マウント・取り外しは、USB が切断されていても受け付ける（メディアは、接続されたときに見える）。
- **ターゲットの BIOS が、HID と MSC の複合デバイスを扱えるか**は、実機で確認する（`TODO(hw-verify)`）。

### 5.2 INQUIRY
- **デバイス種別 5（CD/DVD）**、RMB = 1（取り外し可能）、ベンダー `QUADKVM `（8 文字）、製品 `Virtual CD-ROM  `（16 文字）、版 `0001`（4 文字）。
- 種別を 5 にする手段は A-14 の最初の調査（§1）。**手段が決まらないと、他の部分（SCSI のコマンド）は、先に進められるが、Windows ISO の起動の確認はできない**。

### 5.3 対応する SCSI コマンド（`mmc_scsi`。最小の集合。確定は C-11）
BIOS、UEFI、Linux（sr）、Windows が CD-ROM に対して発行する最小の集合。**文書（MMC / SPC）と照らして、C-11 で確定する**。

| コマンド（オペコード） | 動作 |
|---|---|
| TEST UNIT READY（00h） | メディアがあれば GOOD。なければ NOT READY（3Ah/00h: メディアなし）。メディア変更の直後は、1 回だけ UNIT ATTENTION（28h/00h） |
| REQUEST SENSE（03h） | 直近のセンスを返す |
| INQUIRY（12h） | §5.2。VPD ページは、未対応のページに ILLEGAL REQUEST（24h/00h） |
| MODE SENSE(6)（1Ah）/ (10)（5Ah） | 最小の応答（ヘッダー。ページ 2Ah のドライブの能力、ページ 3Fh のすべて）。MODE SELECT は未対応（ILLEGAL REQUEST） |
| START STOP UNIT（1Bh） | ロードは GOOD（何もしない）。**イジェクト（LoEj = 1、Start = 0）**: PREVENT が掛かっていれば CHECK CONDITION（05h/53h/02h: メディアの取り外しを防止中）。掛かっていなければメディアを取り外す（§5.5） |
| PREVENT ALLOW MEDIUM REMOVAL（1Eh） | 防止フラグを設定・解除 |
| READ CAPACITY(10)（25h） | 最終ブロックの LBA と、ブロック長 2048。メディアなしなら NOT READY |
| READ(10)（28h）/ READ(12)（A8h） | 範囲外は ILLEGAL REQUEST（21h/00h: LBA が範囲外）。SD のエラーは MEDIUM ERROR（03h/11h/00h: 回復できない読み出しエラー） |
| READ TOC/PMA/ATIP（43h） | 形式 0（TOC）、1（マルチセッション情報）、2（生の TOC）。**1 セッション、1 データトラック**（トラック 1: 先頭 LBA 0、制御 = データ。リードアウト 0xAAh: 総ブロック数）。MSF のビットに従う |
| GET CONFIGURATION（46h） | 現在のプロファイル（**DVD-ROM 0010h**。`TODO(hw-verify)`）と、最小のフィーチャー（プロファイル一覧、コア、取り外し可能メディア、ランダム読み出し） |
| GET EVENT STATUS NOTIFICATION（4Ah） | ポーリング形式。メディアのクラス: 新しいメディア、メディアの取り外し、取り外し要求 |
| READ DISC INFORMATION（51h）、READ TRACK INFORMATION（52h） | 最小の応答（完結したディスク、1 セッション、1 トラック） |
| READ SUB-CHANNEL（42h）、GET PERFORMANCE（ACh）、READ CD（BEh）など | 未対応（ILLEGAL REQUEST 20h/00h）。実機で必要と分かったものだけ足す |
| WRITE(10) など書き込み系 | DATA PROTECT（07h/27h/00h: 書き込み禁止）。**イメージは読み取り専用** |

センスキー/ASC/ASCQ の値は、標準の SPC の値（C-11 で文書と照合する）。

### 5.4 メディアの状態（`iso_media`）
- 状態: `EMPTY` / `LOADED(id)`。フラグ: `unit_attention`（メディア変更を、1 回だけ報告する）、`prevent_removal`（ターゲットが設定）、`event_pending`（GET EVENT STATUS で報告する）。
- **マウント**（Web）: `EMPTY` → `LOADED`、または `LOADED` → 別の `LOADED`（差し替え）。いずれも `unit_attention` と新メディアのイベントを立てる。**`prevent_removal` が立っているときの差し替えは 409 `locked_by_target`**（`force` で上書きできる。ターゲットが使っているメディアを取り上げるので、確認させる）。
- **取り外し**（Web `eject`）: `prevent_removal` が立っていれば 409 `locked_by_target`（`force` で取り外す）。取り外すと、次のコマンドが NOT READY（メディアなし）になり、メディアの取り外しのイベントを立てる。
- **取り外し**（ターゲットの START STOP UNIT）: `prevent_removal` が掛かっていなければ、取り外す。Web の状態は `mounted: null`、`ejected_by_target: true` を 1 回だけ報告する。
- **再起動後は、マウントしない**（`ISO_AUTOMOUNT_LAST` は、将来の選択肢。既定 n）。USB の再接続（ターゲットの電源の入れ直し）では、マウントを保つ。

### 5.5 起動（ブート）
El Torito のブートは、ISO の中身（ブートカタログ）が持つ。デバイスは、**ブロックを正しく返すだけ**。ターゲット側の BIOS / UEFI で、起動順位を、この「USB CD-ROM」にするのは、オーナーの操作。UEFI の USB マスストレージのドライバが、デバイス種別 5 とブロック長 2048 の CD を扱えるかは、**一次情報で確認していない**（EDK2 のソースでの確認と、実機の UEFI での確認が要る。`TODO(device-check)`）。**実機で確認する**（`HW_VERIFY` I 章。Linux の ISO と Windows の ISO の両方）。

## 6. アップロードの方式

### 6.1 決定: 分割（チャンク）の PUT + 再開
- ブラウザは、ISO を `chunk_size` ごとに切り（`Blob.slice`）、**`PUT /api/v1/iso/<id>` を順に送る**（1 つの要求 = 1 つのチャンク）。要求のたびに `X-Upload-Offset`（その要求の先頭のバイト位置）を付ける。**サーバーは、`received`（受信済みのバイト数）と一致するときだけ受け付ける**（不一致は 409 `offset_mismatch` と、現在の `received`）。これで、ネットワークが切れても、`GET /api/v1/iso` で `received` を見て、続きから再開できる。
- **`chunk_size` は、`begin` の応答で、サーバーが決める**（既定 128 KiB。`ISO_UPLOAD_CHUNK_KB`、16〜1024）。理由: **`esp_http_server` は 1 つのスレッドで要求を処理する**。1 つの要求の処理中は、同じサーバーの `/ws`（キーボードとマウスの入力）と API が止まる。チャンクを小さくして、1 つの要求を短く（128 KiB で数十 ms）する。映像は専用のサーバー（`video_port`）なので、影響を受けない。**アップロード中の入力の遅延は、実機で測る**（`TODO(hw-verify)`）。許容できなければ、アップロード専用のサーバー（別のポート）に移す（API はそのままで、ホストだけが変わる）。
- **SHA-256 は、受信しながら順に計算する**（mbedTLS）。`finish` で、宣言値（あれば）と比べる。**再起動などで計算の途中の状態が失われたとき**（`incomplete` から再開した場合）は、`finish` が SD を読み直して計算する（`202`、`hashing`。クライアントは `GET` で `ready` になるのを待つ）。
- **アップロードは、同時に 1 つだけ**（409 `upload_in_progress`）。アイドルが `ISO_UPLOAD_IDLE_S`（既定 300 秒）続くと、`incomplete` にする（残す。再開できる）。
- **途中で電源が落ちたとき**: `meta` の `received` は、**パーツの境界ごと**に更新する（そのたびに `f_sync`）。再起動後は `incomplete`（`received` はパーツの境界まで巻き戻る）。続きは、その位置から。

### 6.2 方式の選択肢（おすすめ順。オーナーが変更してよい）
| 順 | 方式 | 理由 |
|---|---|---|
| 1 | **分割の PUT + 再開（採用）** | 数 GB の転送で、途中の切断に強い。1 つの要求が短く、入力を止めない。サーバー側の状態は、`received` だけ |
| 2 | 1 つの大きな PUT（ストリーミング） | 実装が最も単純。ただし、切れたら最初からやり直し。要求が数分続き、その間 `/ws` と API が止まる（採用しない） |
| 3 | multipart/form-data の POST | ブラウザの標準のフォームで送れる。ただし、境界の解析が要り、再開できず、1 つの要求が長い |
| 4 | WebSocket でバイナリを送る | 要求のオーバーヘッドが小さい。ただし、プロトコルを自前で作ることになり、既存の `/ws`（入力）と混ざる |
| 5 | デバイスが URL から取得 | PC を介さない。ただし、TLS の検証、メモリ、SSRF の対策が要る（後続の選択肢） |

## 7. セキュリティと安全

- **認証が必須**。変更する要求（POST / PUT / DELETE）は **Origin 必須**（Host と一致。無ければ 403）。既存の API（`WEB_API.md` §7）と同じ検査（`http_guard`）。
- **パスは、ユーザーの入力から作らない**。ディレクトリ名は `<id>`（サーバーが作る 8 桁の 16 進）。ユーザーの名前は、メタデータの中にだけ置く（表示用）。名前の規則: UTF-8 として正しい、1〜63 バイト、制御文字なし、`/` と `\` なし、前後の空白なし。同じ名前は 409 `name_exists`。
- **上限**: イメージ 16 個（`ISO_MAX_IMAGES`）、1 つのイメージは 16 GiB まで、アップロードは同時に 1 つ、1 つのチャンクは `chunk_size` まで（超過は 413）、JSON のボディは 512 バイトまで（既存の API と同じ）。
- **イメージは読み取り専用**でターゲットに見せる（書き込み系は DATA PROTECT）。
- **SD の抜き取り・故障**: I/O のエラーを、MSC は MEDIUM ERROR で、API は 503 `sd_unavailable` で返す。SD が戻ったら、再初期化する（カード検出の GPIO がないので、定期的な再確認）。**書き込み中のエラーは、アップロードを `incomplete` にして、再開できるようにする**。
- **ログ**: 操作（`begin`、`finish`、`mount`、`eject`、`delete`）の結果と理由を、イメージの `id` と大きさだけ記録する。名前は、記録しない（個人の情報の可能性）。チャンクごとのログは出さない（数万回になる）。進捗は 5% ごと。

## 11. 検討した他の案（記録。変更してよい）

### 保存方式（オーナー決定: 案 1）
| 順 | 案 | 内容と理由 |
|---|---|---|
| 1 | **FAT32 + 分割 + 連続確保（できなければ断片）+ 直接セクタ読み出し（採用）** | IDF を改造しない。32GB のカードは FAT32 が標準。小さなパーツの方が連続した空きを確保しやすい。変換は純 C |
| 2 | exFAT を有効化し、ISO を 1 ファイルで保存 | カードをそのまま使え、1 ISO が 1 ファイル。ただし `ffconf.h` が `FF_FS_EXFAT 0` で固定で、IDF の `fatfs` の複製（6.0.1 に固定）の保守と、特許面の確認が要る。後から、§2 のエクステントの層の下だけを替えて切り替えられる |
| 3 | SD を専用の生領域として管理 | 読み出しは最も単純。ただし領域管理を自前で作る。PC で中身が見えない |
| 4 | 小さな FAT32 + 大きな生領域 | 設定は PC で見え、ISO は連続領域。両方の管理が要る |
| 5 | 4 GiB 超は非対応 | 最も簡単。ただしオーナーの要件（4 GiB 超）に合わない |
